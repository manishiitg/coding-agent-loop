Problem

Muse can call its native request_user_input tool with several questions and multiple options per question. The current tmux adapter reads the visible question widget, moves the cursor to option 1, and presses Enter automatically. The user never sees or chooses the options in chat. The P0 test TestMuseCLIRealAutoFirstOptionThreeQuestionsP0 verifies this current behavior; it does not test a user-facing choice flow. The option name WithAutoSelectRecommended is historical: the implementation chooses the first option even when a different option is marked Recommended.

Current delivery focus: migrate one coding agent at a time from pane-string correctness checks to native structured P0 proof. Keep tmux for keystroke transport and P1 terminal presentation. Start with Muse; the native question UI and a return to hybrid follow after the Muse contract migration is certified. The concrete order and gate are below.

Future product direction: browser profiles stayed on mcp_only after native Claude choosers appeared in tmux and left chat waiting for input it could not send. Reading structured question events and returning the user's selection through a verified input path could let us revisit hybrid later. PLAT-354 documents that path; it does not enable hybrid now.

Current delivery focus: Muse first

Structured question choice in chat: The Muse persistent session now leaves native request_user_input prompts open. A session-scoped reader follows newline-committed user_input_prompt_requested and user_input_prompt_settled rows and emits durable coding_agent_question events keyed by native session and sequence. The chat renders each question, option label, and description; it waits for the settled event before marking a submitted choice complete. The answer endpoint requires the current prompt_id and validates question IDs and option labels against the latest pending JSONL record. It checks the live Muse widget before moving the cursor and sending Enter through tmux, including the multi-question review. A stale prompt returns a conflict. Direct Muse adapter callers retain first-option automatic selection unless they opt into the chat choice mode. The real Muse P0 choice test selected the third option in a single question, then selected the last option in each of three questions on the same retained session and observed answered settlements on 2026-09-23. The composer waits while a choice is pending.

Finish the P0/P1 split for Muse before changing another coding-agent adapter. The next providers are Claude Code, Codex CLI, Cursor CLI, and Pi CLI with Gemini, each with its own native record shape and live proof. The provider cards below are a migration inventory, not approval to change every adapter in parallel.

In the observed logs, runtime.session event.kind=completed has payload.kind=task and can appear repeatedly during one run. model_completed can end with finish_reason=tool_calls. Neither is a whole-turn completion signal. A run-level terminal row is the candidate; its accepted-intent correlation and behavior around pending input still need a live certification before it replaces the interactive waiter. Ordinary initial turns observed locally share the accepted intent ID and run ID; queued or mid-turn intents may join an existing run, so do not require a separate terminal row for every accepted intent. Use the run terminal to finish the foreground chat reply; continue tracking the background task by its task_id/task_stream. Observed Muse transcript contract

Muse's native session.jsonl includes a user_input_prompt_requested event with prompt_id, tool_call_id, and a questions array. Each question has an id, header, question, and ordered options; options have a label and may carry Markdown preview text. A subsequent user_input_prompt_settled event contains the same prompt/tool-call identity, an outcome, and answers with question id and selected_label. A real three-question transcript was inspected locally; the P0 test already reads the requested event to verify the first displayed labels.

The JSONL file is an observation source, not an input API. The current transcript streamer emits assistant text and tool start/end chunks but does not project these question events into chat. The auto-answer path instead parses tmux pixels and sends tmux keys.

Proposed behavior

  1. Tail the active Muse session's session.jsonl by sequence. On a new user_input_prompt_requested, parse the structured questions and present all of them, including option labels and previews, in chat. Correlate the prompt by native session ID plus prompt_id and tool_call_id so resumed sessions and earlier questions cannot be confused with the active prompt.
  2. Disable automatic first-option selection for turns whose choices are presented to the user. Keep the turn pending while the user decides.
  3. On submission, use the existing Muse tmux input path to navigate the live widget and submit the user's selected option for each question. Before sending keys, verify that the visible widget matches the expected question and option labels; if it has changed or vanished, refresh the prompt instead of sending keys against a stale screen.
  4. Confirm completion from the matching user_input_prompt_settled event. Show the recorded selections or an actionable canceled/error state. Avoid duplicate submission across reconnects and repeated event reads.

This is a Muse-specific first implementation. Claude has a related structured source, but its answer record and tmux widget need a provider-specific bridge.

Claude native tools and MCP bridge

The default mcp_only profile passes --tools WebSearch to Claude Code and mounts our api-bridge with --mcp-config and --strict-mcp-config. Claude's own WebSearch remains available. --allowed-tools mcp__api-bridge__*,WebSearch lets those tools run without a permission prompt; it is not the switch that removes native tools. Claude's CLI reference distinguishes --allowedTools from --tools and says the latter does not remove MCP tools.

Enforcement differs by transport

Interactive / tmux: launches with --tools WebSearch, --permission-mode dontAsk, and the bridge MCP config. There is no explicit --disallowedTools list in this path. The optional MCPAGENT_CLAUDE_ENFORCE_HTTP_TOOL_ROUTING setting adds a PreToolUse hook that denies calls outside the registered bridge tools and WebSearch; it is not on by default.

Structured / print: launches with --tools WebSearch and an explicit --disallowedTools list, because this path also uses --dangerously-skip-permissions by default. The denylist is Bash,Read,Edit,Write,MultiEdit,NotebookEdit,Glob,Grep,WebFetch,Task. These are configured deny names, not a claim that every name belongs to Claude's current default set on every platform.

Hybrid: sets --tools default, allowing native tools alongside the bridge. With provider_auto, Claude receives --permission-mode auto and the structured denylist is omitted. The approve_all branch requests native tools but sets only a permission-bypass metadata flag. The interactive argv builder does not read that flag and falls back to dontAsk; the structured argv builder selects --dangerously-skip-permissions yet still adds the native-tool denylist. This is a tool-mode mismatch to fix or test before relying on approve_all for Claude.

Muse background task lifecycle

A native task_backgrounded marker belongs to its parent run_id and task_id. Muse can commit the parent run's terminal=completed before later task status, output, or terminal task events. A live Muse run also produced post-terminal task status and completed rows without a task_backgrounded marker. The reader therefore projects explicit background markers and task lifecycle rows arriving after their parent run's terminal. Foreground completion returns the answer immediately; it does not close the task.

Implemented locally: a session-owned JSONL reader follows newline-committed task rows after the turn's stream channel closes. It matches the background marker and subsequent task rows by run and task ID, emits a bounded coding_agent_background_task event with the native sequence as its stable ID, and stops when the owning session closes. The server persists these events in the interactive chat journal; the chat shows late updates in order after the foreground answer. A synthetic test covers a background marker, foreground terminal, partial appended row, later status, output, and task completion. Separate tests cover unmarked late tasks, the session watcher, and durable replay. The live TestMuseCLIRealBackgroundTaskAfterRunTerminal now passes with post-terminal task rows from a real Muse shell run.

Restart recovery: opening a saved Muse session rescans its native journal from the beginning, including rows committed while the server was down. Native sequence IDs let the chat journal discard already persisted events. A restore test verifies that a completed background task is replayed without waiting for another foreground turn.

Later phase: native multiple-choice UI

  • A live Muse turn asking three questions in one request_user_input call shows all three questions and their ordered options in chat without choosing any answer automatically.
  • The user can choose an option other than the first for each question; Muse receives those choices and continues the same turn.
  • Chat confirms the answers recorded in the matching user_input_prompt_settled event. Reload/reconnect does not replay or resubmit an already settled prompt.
  • A changed or dismissed tmux widget cannot receive keys intended for an earlier prompt; the user sees a recoverable state.

In the 350 newest rollouts, top-level type values were session_meta, turn_context, world_state, event_msg, response_item, token_usage_record, compacted, and inter_agent_communication_metadata.

  • Observed event_msg.payload.type: task_started, task_complete, turn_aborted, item_completed, thread_settings_applied, token_count.

Cursor — RTS store.db

RTS Cursor conversations are SQLite stores, principally meta and blobs, under the service user's XDG Cursor chat root (with a few legacy ~/.cursor/chats stores). The meta object had agentId, latestRootBlobId, name, mode, isRunEverything, and createdAt; some stores also had lastUsedModel or approvalMode. It also contains blobEncryptionKey, which must never be surfaced in chat or diagnostics. The latest root references cumulative message blobs in order, rather than providing an append-only event sequence. The observed message role values were system, user, assistant, and tool; typed content blocks were text, reasoning, redacted-reasoning, tool-call, tool-result, and image. tool-call / tool-result carry toolCallId; many calls are a CallDynamicTool wrapper whose args.toolName names the actual bridge tool. Tool results may be strings or structured JSON.

Across all 927 RTS stores, no native question/choice tool name appeared among tool calls or nested CallDynamicTool names. One nested human_feedback call was a platform bridge tool, not evidence of a Cursor native question widget. This establishes the observed RTS data, not that Cursor can never emit a native question in another version or configuration. The existing Cursor adapter already polls store.db for assistant text and tool call/result chunks; commits can lag the visible terminal by seconds. Separately, Cursor's live --output-format stream-json transport has system, thinking, assistant, tool_call (started / completed), and result event types in the adapter. That stream is a runtime wire source, not another event table in the RTS store.db files inspected here.

Pi CLI with Gemini — local session JSONL

The local pi executable reports version 0.87.0. All 666 local files under ~/.pi/agent/sessions were scanned; 660 contain a Google provider or Gemini model message. Persisted row type values were session, model_change, thinking_level_change, message, and compaction. message.role values were user, assistant, and toolResult; observed content block types were text, thinking, and toolCall. Assistant messages carry provider, model, API, token/cost usage, stop reason, and response ID; tool calls and tool results correlate by ID and carry arguments/results. No question-like native tool call appeared in these local session files.

The adapter also creates a separate per-session markers.jsonl through its bundled Pi extension. Its code emits extension_loaded, session_start, agent_start, turn_start, message_start, message_update, message_end, tool_execution_start, tool_execution_update, tool_execution_end, turn_end, agent_end, and provider_error. These are adapter-added live markers, distinct from Pi's native persisted conversation file. Structured pi --print --mode json can stream the corresponding run/message/tool lifecycle, but that output is a runtime stream rather than the session file.

Pi CLI with Gemini — Confida Hetzner deployment

The Confida server was inspected read-only through its documented SSH port on 2026-09-23. Its deployed Pi executable reports version 0.87.1. Pi sessions are stored under isolated AgentWorks runtime homes in the .pi tree, plus one workspace-local .pi tree; the login user's ~/.pi/agent/sessions is not the complete source. A full find of /srv/confida found 178 Pi session JSONL files, and all 178 contain Google/Gemini activity. Their models were gemini-3.8-flash and gemini-3.7-flash (15,926 and 129 assistant records, respectively). Observed row types were session, model_change, thinking_level_change, and message; message roles were assistant, toolResult, user, and a small number of system rows. Content block types were text, thinking, and toolCall. No question-like native tool call name appeared in the 15,105 recorded tool calls. This is an absence in the observed deployed sessions, not a capability claim for every Pi version.

The service's agent.log and llm_debug.log also contain Pi CLI and Gemini entries through 2026-09-22. No markers.jsonl was retained under the checked runtime home or /tmp; the bundled extension's marker file is a separate temporary runtime signal, while Pi's session JSONL is the durable conversation record.
