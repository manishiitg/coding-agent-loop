## The mental model to design against (current)

- **db/db.sqlite is the source of truth.** A step's real output is the rows it writes through the managed DB tools (or `$DB_PATH` for saved scripted code), not a file. Reports and downstream steps read the db.
- **`context_output` is OPTIONAL.** Use it only for a small explicit handoff a *next step* consumes (it gets injected into that step's prompt), or a deliberate file artifact. If the result is in the db, OMIT it — a hand-written receipt file duplicates the db and drifts (the classic `status: null` while the db is perfect).
- **Validate the source of truth.** `validation_schema` can gate **files** (`files` + json_checks) AND/OR the **db** (`db: [{sql, min_rows, max_rows, checks}]`, read-only queries against db/db.sqlite). Prefer a **db check** when the step writes to the db — gate what was actually produced.
- **`context_dependencies`** is the *file* channel (forward-only, injected into the prompt). Use `[]` when the next step just reads the db. It is NOT required for data flow — the db always is.

PART 1 — VISUAL MAP
Draw the plan so the user sees it at a glance. PART 2 — INTEGRITY CHECKS (structural; severity CRITICAL/WARNING/INFO + one-line fix)
1. **Unpersisted result** — a step does real work but writes neither db rows nor a consumed `context_output`. Its result is lost.
2. **Ungated step** — a step produces durable output but has no `validation_schema` (file OR db check). No automated quality gate.
3. **Stale receipt** — a step writes a `context_output` file that duplicates what it also writes to the db (drift risk). Recommend dropping the file and gating on the db, OR deriving the file from the db.
4. **Broken handoff** — a step lists a `context_dependency` no earlier step produces, OR its description references upstream data that's neither in a declared dependency nor readable from the db.
5. **Routing fall-through** — a routing step's branches don't all converge: a selected branch's terminal step lacks a `next_step_id` to the shared downstream step (or `"end"`), so execution falls into the next sibling branch. CRITICAL.
6. **Routing with judgment** — a routing step has a non-empty description or implies a decision; routing is deterministic and decides nothing. Move the judgment to a prior `message_sequence` step that writes `route_selection.json`.
7. **Orphan reuse not wired** — an orphan step exists but isn't referenced (`orphan_step_ref`) / doesn't declare `shared_with.orchestrator_ids`.
8. **Circular dependency** — A→B→A.
9. **Unjustified prevalidation** — a message_sequence `prevalidation` item is presumed unnecessary by default now that the step-level `validation_schema` is already an automatic final gate with same-conversation repair. Flag every `prevalidation` item unless the plan review can name a specific later item in the same sequence that must not run without it, guarding something costly or hard to undo. A `prevalidation` item that just restates the step's own final schema is pure waste (a repair turn burned every run for nothing a later item couldn't catch anyway) — recommend removing it, not narrowing it.
10. **Outcome/schema conflict** — compare the description's intended outcome and allowed branches with `validation_schema`. Flag checks that contradict that outcome, require data the permitted inputs cannot provide, or require non-null values for outcomes where those values legitimately do not exist. Do not flag a field merely because it appears only in the schema: the executing agent receives the schema proactively. Keep required keys, types, and structural checks in `validation_schema`; use the description for purpose, evidence sources, and business constraints. Make outcome-conditional fields nullable/optional instead of forcing fabricated placeholders. (For example, an intent-based targeting result must not invent numeric follower bounds solely to satisfy validation.)
11. **Undefined required object contract** — a schema requires an object, but neither its nested checks nor an accessible referenced contract defines the contents that a downstream step, evaluator, or user actually needs. A generic object check alone cannot establish those required contents. Add only the necessary nested checks to `validation_schema`, or reference the authoritative contract where the structure is already defined. Do not copy the object's key list or example schema into the step description, and do not add checks for every optional or free-form field. An intentionally flexible object is not a defect just because its full shape is not enumerated.

12. **Fragmentation smell** — two or more of #1 (unpersisted result), #3 (stale receipt), or #4 (broken handoff) fire across steps that share one coherent objective/context (an allocate→execute→verify chain, an investigate→report chain, a scan→draft→publish chain). This is not several independent bugs to patch in place — it is one root cause: the objective was split into more steps than the shared context actually required, so a file/db handoff drifted out of sync at each new boundary the split created. WARNING when two of #1/#3/#4 co-occur on the same chain; CRITICAL when three or more co-occur, or when the split-off work has no live consumer at all (a #4 with nothing downstream ever reading it, not merely a fixable dependency gap). Fix: don't patch each handoff individually — combine the chain into one `message_sequence` per PART 6's agentic-span lens, and name which of that lens's real reasons (credentials/security, independent retries, clean-room, human/routing boundary, context contamination) justifies keeping any step that remains separate. Patching each symptom while leaving the fragmented shape in place treats the wound, not the cause: the next plan edit reliably opens a new stale-receipt or broken-handoff pair at the same boundary.
13. **Cross-step description staleness** — a step's description asserts a fact about how the workflow currently works (a mechanism, an integration, a data source, a join key) that a *sibling* step's description, or `soul.md`, contradicts or has since retired. Unlike #10 (a step's schema disagreeing with its own description), this is two descriptions disagreeing with *each other* after an architecture change was only partially propagated. WARNING; CRITICAL if the stale description governs the primary path of a step feeding a `soul.md` success criterion (the stale side silently degrades from "the reliable path" to "the dead path", with a fallback doing all the real work uncredited). Fix: when a step's description changes what a downstream/upstream sibling produces or consumes, update every sibling description that referenced the old mechanism in the same pass — a plan-change diff that touches one step's contract but not the descriptions of steps that referenced it is incomplete. (Live example: a publisher step's description confirmed a legacy delivery mechanism was fully replaced, but a downstream analytics step's description still named the legacy mechanism as its "reliable" primary match path and the replacement as a mere "fallback" — the fallback was actually carrying all live traffic, uncredited and unaudited.)

PART 3 — STEP-TYPE FITNESS (how to use each; cite the step it applies to)
For each step, confirm it's the right type, and flag mis-modeling:

- **scripted** (`regular` internally) — a deterministic boundary only: API/SDK calls, CLI commands, data fetching, parsing, normalization, or mechanical db/file writes; batch related calls behind one output/retry contract. Create it with `add_scripted_step`, then author and test `<script-dir>/main.py`. Any conversational or judgment-heavy work uses `message_sequence`, even for one work turn. Persist scripted results to the db; gate with a db check; keep `context_output` only for a real consumer.
- **routing** — a DETERMINISTIC N-way switch: no agent, **no description**, decided upstream (a prior message sequence writes `route_selection.json`, or the caller passes `route_selections`); `default_route_id` is the missing-file fallback. **Every branch must converge** to the shared downstream step via `next_step_id` (or end). "Loop/if in a description" is not routing.
- **message_sequence** — one substantial same-context reasoning job plus focused validation/critique/repair follow-ups, or a re-entrant specialist. Its ordered `items` (user_message / prevalidation / foreach / scripted) share one conversation; they are not a checklist of routine sub-actions and should not issue fixed API/CLI calls or parse stable response shapes. Feed it persisted results from upstream scripted fetchers. Reach for a sequence when follow-up turns depend on transient reasoning; as a top-level step the queue runs once, and as an orchestrator route it can be re-entered during the same run.
- **orchestrator** — use only when the parent makes a real runtime orchestration decision: it owns substantive strategy, interprets evidence, chooses further work, changes direction, and synthesizes conclusions. Bounded workers can be scripted or agentic; the parent may reason and execute directly. **A fixed child set and order does not justify an `orchestrator` step.** Tools, isolation, progress visibility, and retries are supporting properties after this eligibility gate. Known script batches (including ten scripts followed by analysis, coverage checks, and a report) belong to the message-sequence design regardless of parallelism. Sequence child support is scoped to scripts only for now; do not add agentic sub-agents to sequences. Keep predetermined isolated agentic tasks as separate message-sequence plan steps. Read `references/plan-design.md`, Step 2, for supported scripted batch items: known independent fixed work belongs in explicit plan steps/dependencies or a declared script batch, while agentic children remain unsupported in sequences. Do not invent dynamic routes or silently drop required isolation. Flag dispatcher-only orchestrators, but do not automatically migrate an existing plan without preserving execution, isolation, validation, and retry behavior. One nested orchestrator layer max.

- **orphan** — a reusable plan-local definition or manual utility agent (data checks, env validation, one-off investigations, or a shared sub-agent several orchestrators reuse). Reuse is explicit: `shared_with.orchestrator_ids` + a route's `orphan_step_ref`.

PART 4 — STORES FITNESS (when to use db vs kb vs learnings; cite the step)
Wrong-store usage is the most common silent design error. Check each step's access against what it actually needs:

- **db/db.sqlite — WHAT this run produced.** State, results, rows, plus durable assets under `db/assets/` (with a metadata row). Every workflow step receives managed read-write access: agentic steps use `query_workflow_db` / `mutate_workflow_db`, while saved scripted code uses `$DB_PATH`. This is the source of truth — results go here, not into files.
- **knowledgebase/ — reusable DOMAIN knowledge across runs.** Business facts, product/catalog info, portal quirks-as-notes, and user-supplied runtime context/preferences/rules (put those in `knowledgebase/context/context.md`). `knowledgebase_access` defaults to `read` (mirrors `learnings_access`); writing is the opt-in — set `read-write` + `knowledgebase_contribution` to add notes. NOT for run results (db) and NOT for execution mechanics (learnings).
- **learnings/ (SKILL.md) — target-specific HOW to run the task.** Reusable execution know-how for the system being operated: selectors/timing, target-service auth/login behavior, third-party API quirks, CLI/SDK patterns, parsing/retry/recovery rules. Shared AgentWorks mechanics (bridge env vars/envelopes, api-bridge routing, Folder Guard internals, managed workflow-DB tool syntax, tool-discovery workarounds, coding-agent tmux/session plumbing) belong only to platform prompts/tool schemas and must never be copied into Plan, Learnings, or KB. `learnings_access` defaults `read`; set `read-write` + a specific `learning_objective` only when target-specific HOW is worth capturing. Not for results (db) or domain facts (kb).
- **soul.md** — the workflow's long-term purpose/persona (Workshop-maintained). Reference it for "what is this workflow for."

Decision rule to surface to the user: *results/state → db; cross-run business knowledge → kb; cross-run execution mechanics → learnings.* If a step writes results into kb/learnings, or tries to keep "how to log in" in the db, flag it.

**Artifact ownership guard:** plan descriptions and message-sequence messages are semantic workflow contracts, not copies of the harness manual. State the domain action, inputs, durable output, failure behavior, and verification outcome. Never embed AgentWorks bridge/auth URLs or environment variables, Folder Guard/CWD implementation details, managed-tool call syntax, `get_api_spec` recovery recipes, or coding-agent session/tmux mechanics. The plan mutation tools reject these unambiguous shared-platform signatures.

PART 5 — GROUPS
Variable groups (e.g. per-account/per-client) run the SAME plan with different variable values. The plan must NOT branch on group identity in prose ("for Saurabh do X, for Anika do Y") — that's either a variable (`$VAR_*`) or, if the flow genuinely differs, a routing step. Flag descriptions that hardcode per-group logic. Check that group-specific values are variables, not literals.

PART 6 — DESIGN LENSES (recommend the better shape, even when nothing is broken)
- **Agentic span / durable-boundary fit** — start with one large `message_sequence` per coherent shared-context span. Modern agents can own a substantial end-to-end outcome in one step, so put proof/provenance requirements, top-level validation, evidence-based double-checking, and repair *inside* that sequence. A step boundary is a **context** boundary: split only when the contexts genuinely must not be shared.

  | Not a reason to split | A real reason to split |
  | --- | --- |
  | a tool call, a source, a screen action | credentials / security separation |
  | a checklist item, a proof check | independent outputs or retries |
  | a routine subtask | clean-room independence |
  | | a human or routing boundary |
  | | context contamination |

  Require the plan to name which right-hand reason applies. Combine adjacent steps that share a context/objective/output and only create pass-through artifacts. When PART 2's Fragmentation smell (#12) fires on this chain, this stops being a soft preference: report the merge as a normal severity-tagged finding with a bounded `recommended_fix` (now/next per #12's severity), not a design note that can be quietly skipped.
- **Validation sequence, not micro-steps** — 2+ regular steps that reread the same context and need each other's transient reasoning → one `message_sequence`. Split only when the context should not be shared or the boundary buys independently rerunnable validation/retry isolation, clean-room auditability, a downstream artifact, or tool/security separation. Give its first work turn the complete outcome, then add only evidence-based verification/critique/repair turns or genuine intermediate gates; flag one-message-per-routine-action sequences too.
- **Scripted acquisition, agentic processing** — fixed API/SDK calls, CLI commands, deterministic pagination, fetch/parse/normalize logic, and mechanical persistence belong in scripted regular steps. Batch related fetching under one source/auth/retry/output contract, validate freshness/provenance/errors, then feed the durable rows/artifacts into a large message sequence for judgment. Flag plans that repeatedly spend LLM turns on deterministic retrieval or parsing.
- **Gate everything** — every produces-output step needs a `validation_schema`; prefer db checks on the source of truth. A gate catches drift the moment it lands, not three steps downstream.
- **Prevalidation is the exception, not the default** — this cuts the other way from "gate everything": the step-level `validation_schema` is already the automatic final gate with same-conversation repair, so an intermediate `prevalidation` item inside a message_sequence needs to earn its place. It belongs only when a later item in the same sequence must not run without it, protecting something costly or hard to undo (a paid tool call, a fan-out, an external side effect). Recommend removing one that just restates the eventual final schema — it burns a repair turn on every single run and catches nothing a later item wouldn't have caught by failing the final gate anyway.
- **Human gates** — consequential actions need explicit authorization at their action boundary. Reuse existing valid authorization; for a new fixed-choice checkpoint use a human-decided branch, or a durable approval/consumer flow. Consult `references/human-in-the-loop.md`; do not add a checkpoint just to repeat approval already given.
- **Naming** — "process_data"/"do_step" are generic; "classify_emails_by_buyer_intent" makes the plan self-documenting.
- **Mode** — deterministic API/CLI/SDK/data-fetch/parse/transform steps start **scripted** and should have `main.py` authored and tested in Workshop. Judgment, synthesis, adaptive discovery, and browser/UI work stay **agentic**. The 10+-run evidence bar is only for *freezing* a proven script with `lock_code`, not for declaring an obviously deterministic step scripted. When `technical_review` has recorded tool-call trace evidence that a step's actual behavior is deterministic and identical in shape across runs, ground the scripted-candidate finding in that real evidence rather than the description alone — a description that reads as agentic can still be masking a step whose real tool-call sequence never varies.

For each recommendation give: **what's there now** (one quoted sentence), **what to consider** (better shape + concrete example), **why** (which practice it serves).
